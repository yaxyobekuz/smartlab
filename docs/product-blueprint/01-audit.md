## infra — Audit

The "infra" here is a clean, registry-driven **content-delivery shell** — not a learning platform. What's genuinely impressive is the `LabWorkspace` shell (unified left-info / 3D-center / right-AI layout with VR/cardboard/walk immersive modes) and the **grounded "Mira AI" tutor**, which streams over SSE and injects the active model's real data + a tool-calling protocol (`control_scene` / `navigate_topic` / `select_item` / `start_quiz`). What's thin is everything the parallel teams will hook into: there is **no quiz engine, no XP/coins/levels, no achievements, no streaks, no leaderboard, no progress tracking, and no user/profile in the lab** — the lab is fully anonymous, has zero persistence (no `localStorage`/`sessionStorage`/`indexedDB` anywhere under `lab/`), and the only gamification-flavored files (`BottomNavbar.jsx`, `UserProfileCard.jsx`) are dead owner-panel template leftovers wired to nothing.

### Highest-leverage upgrades (specific to this area)

- **Collapse the registry↔`PAGES` duplication into one source.** `subjects.js` lists topics and `TopicPage.jsx` independently hardcodes `"biology/anatomy": lazy(() => …)`. Add the component ref (or a `status`/`ready` flag) to the registry and generate the map from it — otherwise a topic can ship in the nav but 404, and every "coming soon"/gating feature has to re-encode the same list.

- **Persist the action journal into a real progress layer.** `recentActions` (the 12-item ring buffer in `SceneControlProvider`) already knows exactly which models a user opened — it's thrown away on reload. A shared `useProgress` keyed by `subject/topic` (localStorage first, account-backed later) built on top of the existing `logAction` call gives you "continue learning" on the Landing/Subject pages and a single source of truth the parallel XP/streak team can read from — with minimal new plumbing.

- **Turn `start_quiz` into an actual quiz engine instead of a one-off card.** Today the AI emits a single MCQ into the chat with no score, no persistence, and no per-topic content. Add per-topic question sets to the registry (authored or AI-generated-and-cached) plus an attempt→result flow, so the same `QuizCard` UI can back XP, streaks, and completion — the client-side rendering is already done, it just has nothing structured behind it.

- **Enrich `subjects.js` with curriculum metadata now.** It currently carries only `title/short/icon/color`. Difficulty, estimated time, prerequisites, learning objectives, and a `hasQuiz` flag are prerequisites for progress %, prereq gating, and XP weighting — cheap to add here, expensive to retrofit once features depend on the shape.

- **Delete the dead template gamification/profile components before the real build starts.** `BottomNavbar.jsx` ("Tangalar"/Coins → `/transactions`) and `UserProfileCard.jsx` are unrendered owner-panel leftovers modeling a different app. If coins/profile are coming to the lab, build them lab-native against the new progress layer — leaving these around invites someone to wire up the wrong data model.

### Highest-leverage upgrades (specific to this area)

1. **Unify the lab bench with the real datasets.** Today `useLabBench` recognizes products against 16 molecules in `molecules.js` and fires 8 hardcoded rules in `reactions.js`, while `moleculeLibrary.js` holds 240 molecules and `elements.js` holds 118 elements next door. Index products off `moleculeLibrary` (via the existing `compositionKey`) and derive reagents from the periodic data — this turns a demo into a real sandbox with almost no new content authoring.

2. **Fix the ElementModal oxidation-state bug and add a property overlay.** `ElementModal.jsx` reads `b.commonOxidationStates` (level1) but the values are stored at `level3_properties.electronic.oxidationStates`, so a field students expect is silently missing. Same numeric data (`electronegativity`, `atomicRadius`, `firstIonization`) is already present per element and unused visually — a "colour the table by property" toggle is high-impact, low-cost, and pure data reuse.

3. **Retire the vendored Zperiod island.** The `Calculators` tab mounts ~13 K lines / 472 KB of non-React code via `dangerouslySetInnerHTML` + manual event wiring, with its own CSS and English-only locale, violating the app's shadcn/Uzbek/TanStack conventions. Molar-mass and the balancer can be reimplemented natively on top of `molecules.js#parseFormula` and `reactionTemplates`, cutting bundle size and an entire foreign maintenance surface. Delete `utils/equationBalancer.js` (dead identical copy) and the dead `chemMath` exports at the same time.

4. **Rebuild Atoms as a projection of the periodic table.** The Bohr renderer in `AtomModel.jsx` is fine; the problem is `data/atoms.js` hand-lists only 5 atoms while `elements.js` already carries protons, neutral electrons, and electron configuration for all 118. Compute the shell array from configuration and let users open Atoms directly from an element card — one small function upgrades 5 → 118 atoms and links two currently-isolated pages.

5. **Add the assessment/progress seam the app is planning.** The Worksheet already auto-grades and the lab bench already keeps a journal, but nothing emits a structured result. Have these (and a future ion/compound builder) return a typed attempt payload so the parallel quiz/progress/gamification layer has a concrete chemistry hook to consume instead of being retrofitted later.

## electronics — Audit

Honest summary: For a single topic (`electronics/arduino` → `CircuitPage`) this is the most technically ambitious area in the lab — a genuinely working Tinkercad-style 2D SVG builder wired to a from-scratch Arduino-sketch interpreter (regex C→JS-generator transpiler) that runs live on a cooperative virtual clock, with per-component reactive visuals (LED glow, PWM fade, servo sweep, motor spin, buzzer pulse, live pot/photoresistor drag). It is far deeper than a toy. But it is an electrical *connectivity* simulator, not a *circuit* simulator: resistor values, current, and Ohm's law don't exist; `Serial` is fully stubbed; there is no persistence, no touch support for adding parts, and the pedagogical text that's already in the data is never shown.

### Highest-leverage upgrades (specific to this code)

- **Wire up the stubbed `Serial` (P0).** `board.js:104` makes `print/println` no-ops, so learners have no way to inspect variables — the single most-used Arduino debugging affordance. Route `Serial.print*` into the sim store and render a monitor pane in the empty right-column footer of `CodeEditor.jsx`. Highest impact for the least architectural change.

- **Make the resistor real (P1).** `ohms` flows through the Inspector, templates, and resistor band-colors but is grep-confirmed *never read by `board.js`/`netlist.js`* — so the sim can't teach current limiting, the one thing resistors are for. A minimal series-resistance / current model (current ∝ V÷ΣR, brightness/heat from it) turns the inspector's ohms selector from a placebo into a lesson and unlocks "LED burned out — rezistor kichik" feedback.

- **Add non-blocking miswiring diagnostics (P1).** The netlist already computes `netReachesGnd` / `netReachesPower` / `arduinoPinOf`; reuse them to surface gentle Uzbek hints ("LED teskari ulangan", "GND ulanmagan", "rezistor yo'q") instead of a silently-dark LED. This is the difference between a sandbox and a teacher.

- **Surface the lesson text and persist work (P1).** Each template already carries an Uzbek `description` that no component renders — show it as a one-line brief when a template loads, and add localStorage autosave + a shareable JSON/URL export (there is zero persistence today, so refresh = total loss). Both are small and directly raise retention.

- **Fix touch onboarding (P1).** `Palette.jsx` adds parts via HTML5 `draggable`+`dataTransfer`, which doesn't fire on touchscreens — on a phone/tablet a user can pan the canvas but can never place a component, a hard blocker for a *public web* app. Add a tap-to-add fallback (tap tile → drop at viewport center) alongside the existing DnD.

Hook point for the parallel systems: a **challenge/goal mode** would slot naturally on top of `templates.js` + the netlist (e.g. "LEDni 2x tez miltillat" with a pass-check reading `board.readVisuals` / pin timing) — the sim already exposes everything a checker needs, and this is where the not-yet-built quiz/progress engine should attach.
